# AI migration guide: replace the Sampler pipeline

You are migrating a PowerShell module repository from the legacy Sampler/GitVersion/InvokeBuild pipeline to the build and release pipeline used by [hanpq/PSLogs](https://github.com/hanpq/PSLogs). This folder (`pipeline-migration-kit/`) was copied to the root of the repository you are working in. It contains:

| Path | Purpose |
| --- | --- |
| `copy/` | Generic pipeline files. Copy them unchanged. |
| `adapt/` | PSLogs versions of files that contain module-specific content. Use them as references and adapt them. |
| `kit-files.psd1` | Inventory of `copy/`, `adapt/`, and obsolete paths under `Remove`. |
| `KIT-VERSION.txt` | PSLogs commit the kit was exported from. |
| `MAINTAINER-SETUP.md` | GitHub settings the maintainer must change. You cannot do these; reference them in your summary. |

Read this whole document before changing anything. Follow the steps in order.

## Ground rules

- Work on a new branch, for example `build/replace-pipeline`. Never push, open pull requests, create tags, publish modules or change GitHub settings unless the maintainer explicitly asks.
- Do not change module behavior. Only touch files under `source/` where this guide says so (the module manifest and directory casing).
- Never commit secrets, tokens or credentials.
- The pipeline files in `copy/` are tested in PSLogs. Do not "improve" them. The only allowed changes are the module profile edits in [Step 5b](#step-5b-apply-the-module-profile). If a file does not work for this module for any other reason, stop and report why instead of rewriting it.
- When something does not fit this guide (see [Stop conditions](#stop-conditions)), stop and ask the maintainer.
- The kit folder itself must not be committed. Delete it in the last step.

## How the new pipeline works

Understand this before migrating, so you can judge what the old files did and whether anything is lost.

- `build.ps1` replaces Sampler. Tasks: `Verify` (default: build + all tests), `Build`, `Test`, `Package`, `Clean`, `InstallDependencies`. `-TestSuite All|Module|Infrastructure` selects `tests/Unit` + `tests/QA` (Module, with code coverage) or `tests/Build` (Infrastructure). Dependencies are pinned in `RequiredModules.psd1` and saved to `output/RequiredModules`. Coverage is measured on the built `.psm1` and mapped back to `source/public` and `source/private` by `scripts/ConvertTo-SourceCoverage.ps1`; the build fails if no lines map there (for example a module with only `classes`), so report that instead of lowering the target.
- The module is built with ModuleBuilder from the single manifest `source/<ModuleName>.psd1` into `output/<ModuleName>/<Version>/`. `source/prefix.ps1`, `source/suffix.ps1` and the `source/en-US`, `source/include` and `source/format` folders are copied when they exist. The singular `format` folder holds formatting assets such as `.ps1xml` files.
- The module name comes from the manifest file name. The default version comes from `.release-please-manifest.json`, which tracks stable releases only. Published beta builds use the immutable tag's version through `build.ps1 -Version`; they never update tracked versions (GitVersion is gone).
- `.github/workflows/ci.yml` runs on pushes and pull requests to `main`, except pushes that only change release metadata (merged release PRs). It never releases.
- `.github/workflows/release-please.yml` ("Prepare stable release") prepares stable PRs only on explicit main-branch dispatch, with `skip-github-release: true`. Merging the manually prepared, same-repository pending release PR triggers release-only finalization on its close event, with `skip-github-pull-request: true`. Ordinary pushes and ordinary PR merges never prepare or refresh release PRs. The standard action owns versions, changelog, tags and releases; there is one stable config and no custom finalization script or promotion label.
- `.github/workflows/beta.yml` ("Publish beta") is manual and main-only. It refreshes the normal stable PR with `skip-github-release: true`, then `scripts/New-BetaRelease.ps1` reads that PR's immutable manifest for the inferred next stable version and appends the next `-betaNNN` counter. It tags the dispatched source SHA and creates a GitHub prerelease using `RELEASE_PLEASE_TOKEN`, which triggers the ordinary Release workflow. It never writes a beta changelog section or modifies tracked versions. Do not replace this with a second Conventional Commit parser.
- `.github/workflows/release.yml` runs when a GitHub release is published. It builds and tests the tag, attaches a ZIP to the release, publishes to the PowerShell Gallery, optionally to ProGet (`PSTOOLS_*` secrets), and, for stable releases, updates the module docs in `hanpq/getps.dev` (`GITHUBTOKEN` secret).
- Release notes are generated by Release Please from Conventional Commit messages. Nobody edits `CHANGELOG.md` by hand anymore.
- Stable changelogs cover commits since the previous stable release because beta tags never advance the stable manifest baseline. Historical beta sections stay untouched. Stable is rebuilt/tested independently; it is not an exact-source promotion of the last beta. There is no post-beta allowlist, duplicate-dispatch marker or manual beta version input. Repeated dispatches intentionally allocate successive beta counters for the same stable candidate.
- Release PR CI rejects prerelease versions in the stable baseline. Stable PR/tag builds use their matching changelog section; ordinary untagged builds still use `[Unreleased]`. Beta builds use short preview notes without reading the changelog. Gallery notes are shortened on whole lines to 10,000 characters including a full-changelog link derived from the repository's changelog comparison URL. No PSLogs-specific URL needs adapting; do not hardcode one. Oversized single lines fail explicitly, and the built manifest is checked against the 10,600-character Gallery limit.
- The kit defaults to the PSLogs profile: a public module published to the PowerShell Gallery with docs on getps.dev, and tested on Linux, macOS, Windows (PowerShell 7) and Windows PowerShell 5.1. Modules that are not published to the Gallery or do not support every platform get a trimmed version in [Step 5b](#step-5b-apply-the-module-profile).
- Nothing in the pipeline requires a public repository. Private repositories work unchanged; the maintainer-side differences (Codecov plan, Actions minutes, badges) are in `MAINTAINER-SETUP.md`.

## Step 1: Detect the mode

- **Migration mode:** the repository has Sampler files such as `build.yaml`, `Resolve-Dependency.ps1` or `GitVersion.yml`. Do all steps.
- **Update mode:** the repository already has `scripts/Get-BuildProject.ps1` and `.github/workflows/release-please.yml`. It was migrated before and should get the newer kit. Do [Update mode](#update-mode) instead of steps 3 to 6.

## Step 2: Inspect the repository

Collect the following facts. You need them later and must include them in your final summary.

1. **Module name.** `source/` must contain exactly one `*.psd1`. Its base name is the module name.
2. **Repository slug** (`owner/name`) from `git remote get-url origin`.
3. **Latest published stable version.** Find the highest numeric `v<Major>.<Minor>.<Patch>` tag, excluding every prerelease tag. Confirm that it has a published, non-draft, non-prerelease GitHub release. Cross-check the corresponding stable changelog entry and, for Gallery modules, `Find-Module <ModuleName>` without `-AllowPrerelease`. For ProGet-only modules, have the maintainer confirm the latest stable package. A newer beta is normal and does not change this baseline. If the stable tag/release/package disagree, or no stable baseline exists, stop and ask.
4. **Old build settings** in `build.yaml`: `CopyPaths`, `Prefix`, `Suffix`, `NestedModule`, `Encoding`, the `BuildWorkflow` tasks, the `Pester` section (`CodeCoverage`, `ExcludeFromCodeCoverage`, test paths and tags) and `GitHubConfig`. The new build supports optional `CopyPaths: [en-US, include, format]` (including legacy `Format` after renaming), `Prefix: prefix.ps1`, `Suffix: suffix.ps1`, an empty `NestedModule`, coverage target 1 and `ExcludeFromCodeCoverage: include`. Check that every legacy copy path's assets are preserved.
5. **Custom build tasks** in `.build/*.ps1` and any other task files. PSLogs had `Publish.PSGallery`, `Publish.Proget`, `Publish.Release.To.GitHub`, `Publish.Create.ChangeLog.GitHub.PR` and `Publish.Create.Docs.GitHub.PR`; all of them are covered by the new workflows. Anything else (code signing, extra artifacts, external services) is not covered.
6. **Old workflows** in `.github/workflows/` and every `secrets.*` they reference.
7. **Dependencies** in the old `RequiredModules.psd1`. Note entries that are not build tooling (Sampler, Sampler.GitHubTasks, InvokeBuild, Pester, PSScriptAnalyzer, Plaster, ModuleBuilder, ChangelogManagement, Configuration, Encoding, PlatyPS, Alt3.Docusaurus.Powershell, PowerShellGet, PackageManagement, Microsoft.PowerShell.PSResourceGet, MarkdownLinkCheck, DscResource.*).
8. **How unit tests import the module.** Look at the top of a few files in `tests/Unit`.
9. **Publish targets.** Determine whether the old pipeline publishes to the PowerShell Gallery and to ProGet. Gallery evidence: a `publish_module_to_gallery` or `Publish.PSGallery` task in `build.yaml` or `.build/`, `Publish-Module`/`Publish-PSResource` to `PSGallery` in workflows or task files, or the `GALLERYAPITOKEN` secret. ProGet evidence: a `Publish.Proget` task or the `PSTOOLS_*` secrets. Also note whether the repository is private (`gh repo view --json visibility`, or ask). A module counts as **Gallery-published** only when the old pipeline publishes it there.
10. **Supported platforms.** Determine which of the four CI targets (Linux, macOS, Windows with PowerShell 7, Windows PowerShell 5.1) the module supports. Use, in this order: the operating systems and shells the old workflows or `azure-pipelines.yml` actually tested on, `CompatiblePSEditions` and `PowerShellVersion` in the manifest (`Core` only or `PowerShellVersion` 6 or higher excludes Windows PowerShell 5.1), and README statements. Keep a target only if the old pipeline tested it or the manifest and README clearly support it.

### Stop conditions

Stop and ask the maintainer before continuing if any of these is true:

- `source/` contains more than one `*.psd1`, or the module is not built from `source/` with ModuleBuilder.
- `build.yaml` configures `NestedModule` entries, `CopyPaths` whose names do not match `en-US`, `include` or singular `format` (ignoring case), a prefix or suffix file other than `prefix.ps1`/`suffix.ps1`, or an `Encoding` other than UTF8. Stop if a listed copy path is missing or its contents cannot be preserved.
- A custom build task, workflow or test does something the new pipeline does not cover (for example code signing with the `PFX_*` secrets, DSC resources, extra packages).
- The old `RequiredModules.psd1` contains a module the tests need at runtime that is not build tooling.
- Release tags do not follow `v<Major>.<Minor>.<Patch>`, or the current version is unclear.
- An update still tracks a beta version, has an obsolete open release PR, or has a merged pending release. Follow the transition checks in Update mode before replacing any pipeline files.
- The old pipeline publishes neither to the PowerShell Gallery nor to ProGet, or publishes somewhere else.
- The supported platforms are unclear or contradict each other (for example the old pipeline tested Linux but the manifest only allows `Desktop`).

## Step 3: Remove the legacy pipeline

Delete these files when they exist:

- `build.yaml`
- `GitVersion.yml`
- `Resolve-Dependency.ps1`
- `Resolve-Dependency.psd1`
- `azure-pipelines.yml`
- PowerShell task files under `.build/` (`*.build.ps1`, `*.ib.tasks`, other `*.ps1`). Keep non-script assets such as images that the README or docs link to. Delete `.build/` if it becomes empty.
- Old workflows in `.github/workflows/` that build, test, publish or release, for example `build.yml` and `pullrequest.yml`. Keep unrelated workflows (for example CodeQL, stale issues, Dependabot) unchanged.
- `output/` contents are not tracked and can be ignored.

## Step 4: Copy the generic files

Copy every file from `copy/` to the same relative path in the repository root, overwriting existing files. Do not edit them, apart from the module profile edits in step 5b. `kit-files.psd1` lists them under `Copy`.

`RequiredModules.psd1` is replaced by the kit version. If step 2 found a runtime dependency that tests need, you should already have stopped.

## Step 5: Adapt the module-specific files

Normalize directory names recursively under `source/` to lowercase before adapting files. Preserve canonical PowerShell culture names such as `en-US` (and correct mis-cased culture names such as `en-us`): PowerShell uses them to find localized help. Rename legacy `Public`, `Private`, `Include`, `Format` (singular) and any other non-culture directories, including nested ones. On case-insensitive filesystems, use two `git mv` commands per tracked directory via a temporary name (for example `git mv source\Format source\format-tmp` followed by `git mv source\format-tmp source\format`); for untracked directories use a corresponding two-step filesystem move. Check for case-colliding destinations before moving and stop rather than merging or overwriting them. Update path references in scripts, tests, manifests, documentation and configuration to the exact new casing, including source mappings and packaging paths. Do not rename files or change module behavior.

For each file in `adapt/`, start from the kit version, then apply the changes below. "PSLogs-specific" means content about logging, runspaces or PSLogs features.

| File | What to do |
| --- | --- |
| `BUILDING.md` | Replace with the kit version. Replace `PSLogs` with the module name everywhere. Remove the PSLogs-specific sentences about background logging, the `LoggingQueueConsumer` runspace and **PowerShell Attach to Logging**, and remove the **Reuse this pipeline in other modules** section. Keep everything else. Add this line at the end: `Pipeline kit: hanpq/PSLogs@<Source commit from KIT-VERSION.txt>`. |
| `ModuleDebug.ps1` | Keep the first eight lines of the kit version (they import the built module). If the repository already has a `ModuleDebug.ps1`, keep its scenario code below the import and remove any old import or build logic. Otherwise add a short comment such as `# Add manual test scenarios for <ModuleName> here.` Remove all PSLogs code. |
| `tests/QA/module.tests.ps1` | Replace with the kit version. It no longer depends on ChangelogManagement or Sampler, and it does not compare branches against `origin/main`. If the repository version has deliberate module-specific checks, port them into the kit version and mention it in the summary. |
| `.vscode/launch.json` | Replace with the kit version and remove the **PowerShell Attach to Logging** configuration. Keep any other configurations the repository had that are still valid. |
| `.vscode/settings.json` | Merge. Keep the repository's existing settings. Add the `github.copilot.chat.commitMessageGeneration.instructions` setting from the kit version. Add the generic `cSpell.words` that the pipeline uses (`APITOKEN`, `GALLERYAPITOKEN`, `GITHUBTOKEN`, `PSTOOLS`, `hanpq`, `LASTEXITCODE`, `notmatch`, `psake`, `PSHOME`, `mkdocs`, `platyps`, `Powershellgallery`) to the existing list. Do not copy PSLogs-specific words. |
| `.github/CONTRIBUTING.md` | Keep the repository's file. Make sure it tells contributors to run `./build.ps1`, links to `BUILDING.md` and contains the Conventional Commits paragraph from the kit version. Remove instructions about Sampler, GitVersion, `Resolve-Dependency` or editing `CHANGELOG.md` by hand. |
| `.gitignore` | Merge. Make sure `output/` is ignored. Keep the repository's other entries. |
| `.markdownlint.json` | Merge. Make sure `MD013`, `MD024` and `MD034` are `false`, because Release Please generates long lines, repeated headings and bare URLs in `CHANGELOG.md`. |

Then check these files, which are not in the kit:

- **`source/<ModuleName>.psd1`:** set `ModuleVersion` to the current released version from step 2. Make sure `PrivateData.PSData` contains `Prerelease = ''` and `ReleaseNotes = ''`; the build writes to both. Remove generated header comments that mention Sampler or Plaster if present. Change nothing else.
- **`README.md`:** update build status badges and links that point to old workflows (for example `build.yml`) so they point to `ci.yml`. Leave the rest alone.
- **`.github/PULL_REQUEST_TEMPLATE.md`:** replaced in step 4. If the old template had module-specific checklist items, mention them in the summary.
- **`codecov.yml`:** replaced in step 4. If the old file had a coverage target, mention the old and new target in the summary.
- **`tests/Unit/*`:** leave unchanged unless they fail after the migration. Many Sampler-era tests find the built module under `output/<repository folder name>/`, which only works when the repository folder name equals the module name. If they fail for that reason, change them to locate `output/<ModuleName>/` using the manifest name in `source/`.

## Step 5b: Apply the module profile

Skip this step if the module matches the PSLogs profile: Gallery-published and supporting all four CI targets (step 2, items 9 and 10). Otherwise make only the edits below to the copied files.

**Not published to the PowerShell Gallery** (for example a ProGet-only module in a private repository):

1. In `.github/workflows/release.yml`, delete the **Publish to PowerShell Gallery** step.
2. In the same file, delete the three documentation steps (**Check documentation update credentials**, **Check out getps.dev**, **Update getps.dev documentation**). getps.dev only documents public modules. Delete `scripts/Update-Docs.ps1`.
3. ProGet is now the only publish target, so it must not be skipped silently. In the **Publish to ProGet** step, replace the `Write-Host 'ProGet publishing skipped; ...'` and `exit 0` lines with `throw 'The PSTOOLS_APITOKEN secret is required to publish a release.'`.
4. In `README.md`, remove PowerShell Gallery badges, Gallery install instructions that cannot work for this module, and getps.dev links. If the repository is private, replace shields.io badges that read GitHub data (they cannot see private repositories) with GitHub's own badge: `https://github.com/<owner>/<repo>/actions/workflows/ci.yml/badge.svg`.
5. In `BUILDING.md`, change the sentence about publishing to the PowerShell Gallery so it says the module is published to ProGet.

**Not all platforms supported:**

1. In `.github/workflows/ci.yml`, delete the matrix entries for unsupported targets: `Linux PowerShell` (Linux), `macOS PowerShell` (macOS), `Windows PowerShell` (Windows, PowerShell 7) and `Windows PowerShell Desktop` (Windows PowerShell 5.1). Keep the `infrastructure` job on `ubuntu-latest`; it tests the pipeline scripts, not the module.
2. `release.yml` builds and tests the release on `ubuntu-latest`. If Linux is not supported, change the job's `runs-on` to `windows-latest`. If the module only supports Windows PowerShell 5.1, also change the **Build and test release** step to `shell: powershell`. Leave the other steps on `pwsh`.

**Record the profile.** Add a section at the end of `BUILDING.md`, just above the `Pipeline kit:` line, that lists every edit you made in this step, for example:

```markdown
## Pipeline customizations

- Not published to the PowerShell Gallery: Gallery and getps.dev steps removed from `release.yml`, `scripts/Update-Docs.ps1` deleted, ProGet publishing required.
- Windows only: Linux and macOS removed from the CI matrix; releases build on `windows-latest`.
```

Update mode uses this section to re-apply the same edits after copying newer kit files. Mention the profile in the summary.

## Step 6: Create the release metadata

Use the current released version `X.Y.Z` from step 2.

1. Create `.release-please-manifest.json`:

   ```json
   {
     ".": "X.Y.Z"
   }
   ```

2. Create `version.txt` containing `X.Y.Z` followed by a newline.
3. Keep the existing `CHANGELOG.md` history. Make sure:
   - It starts with a `# ...` title and the introduction paragraph, like the kit's PSLogs changelog. Release Please inserts new versions above the first `## [` heading.
   - It contains a `## [Unreleased]` heading. Ordinary untagged builds use its content as release notes; stable PR/tag builds use their matching version section. Beta builds do not read the changelog. The heading may be empty.
   - It still contains at least one released entry in the `## [X.Y.Z] - YYYY-MM-DD` format. The QA tests check both headings.
   - If `## [Unreleased]` contains unreleased entries, leave them and tell the maintainer. They will not appear in the next generated release notes.
4. Confirm that the tag `vX.Y.Z` and a published GitHub release for it exist (`git ls-remote --tags origin vX.Y.Z`; check the release on GitHub if you have access, otherwise ask the maintainer to confirm). Release Please uses that release as the starting point for the next release notes. Without it, the first release PR would include the whole Git history. If either is missing, stop and ask.

## Step 7: Validate

Check that every directory under `source/` is lowercase except canonical culture directories (for example `en-US`). Run this PowerShell check and resolve every reported path before continuing:

```powershell
$cultureNames = [System.Globalization.CultureInfo]::GetCultures([System.Globalization.CultureTypes]::AllCultures).Name
$invalidDirectories = @(Get-ChildItem -LiteralPath source -Directory -Recurse | Where-Object {
    if ($_.Name -cin $cultureNames) { $false }
    elseif ($_.Name -in $cultureNames) { $true }
    else { $_.Name -cne $_.Name.ToLowerInvariant() }
})
if ($invalidDirectories.Count) {
    throw "Source directories must be lowercase or canonically named cultures: $($invalidDirectories.FullName -join ', ')"
}
```

Run from the repository root:

```powershell
pwsh -NoProfile -File ./build.ps1
```

This installs the pinned dependencies, builds the module and runs all test suites. If Windows PowerShell 5.1 is available and the module supports Desktop, also run:

```powershell
powershell -NoProfile -File ./build.ps1 -Task Test -TestSuite Module
```

Then:

1. Fix failures caused by the migration. Do not change `copy/` files to make tests pass; if a kit file fails, stop and report it.
2. Do not fix failures in module code that are unrelated to the migration. Report them.
3. Search the repository (excluding `output/` and the kit folder) and remove or update remaining references to `Sampler`, `GitVersion`, `Resolve-Dependency`, `build.yaml`, `InvokeBuild`, `ChangelogManagement`, `-ResolveDependency` and `-tasks`.
4. Run `git status` and review that only intended files changed.

## Step 8: Finish

1. Delete the `pipeline-migration-kit/` folder.
2. Commit everything in one commit. Use the message below so the migration itself does not request a release, and add the Co-authored-by trailer your tooling requires:

   ```text
   build: replace Sampler pipeline with build.ps1 and Release Please
   ```

3. Give the maintainer a summary with:
   - Module name, repository slug and the release version you recorded.
   - The module profile: publish targets, repository visibility, supported CI targets and the edits from step 5b.
   - Files deleted, copied, adapted and created.
   - Source directories renamed, and confirmation that formatting assets (if present) are in the built module and package.
   - Anything from the old pipeline that is not covered by the new one.
   - Old and new code coverage target, and module-specific PR template items that were dropped.
   - Test results, including failures unrelated to the migration.
   - The secrets the old workflows referenced, and which of them the new workflows still use after step 5b: `RELEASE_PLEASE_TOKEN`, `GALLERYAPITOKEN`, `PSTOOLS_APITOKEN`, `PSTOOLS_SOURCE`, `GITHUBTOKEN`, `CODECOV_TOKEN`.
   - A reminder to follow `MAINTAINER-SETUP.md` before the first release (you deleted the kit folder, so tell them it is in the PSLogs repository under `pipeline-migration-kit/`).

## Update mode

The repository already uses this pipeline and gets a newer kit.

### Transition checks before overwriting files

This kit replaces the earlier beta-PR/stable-promotion model. Do these checks even if the repository has no record of its previous kit inventory:

1. Establish the latest published **stable** baseline as described in step 2. Read `.release-please-manifest.json` and `version.txt`; both must match that stable version. Newer published beta tags/packages may remain and are used to continue beta counters.
2. If the manifest or version file still tracks a beta, **stop before editing**. Ask the maintainer to finish the old stable promotion with the old pipeline, or obtain explicit approval for a one-time baseline repair from the verified latest stable tag's metadata. Do not silently strip `-betaNNN`, choose the latest beta as the baseline, or rewrite versions/history. If the latest stable tag has no usable metadata, stop rather than inventing it.
3. Inspect the open `release-please--branches--main` PR and all merged PRs still labeled `autorelease: pending`. Have the maintainer close obsolete open beta/promotion PRs without merging them before the upgrade is activated. Finish failed merged-release finalization using the old pipeline first. Only the maintainer may clear a stale pending label after confirming its matching tag and published GitHub release already exist. Never clear labels just to unblock the new action. Do not modify PRs or labels without approval.
4. Inspect the unreleased commit range for `Release-As:` footers that request a beta. They would now affect the stable-only action: stop and ask the maintainer to resolve them before activating the upgrade. Also report any stale unpublished future changelog section. Leave published historical beta sections, tags, releases and packages unchanged.

Stable preparation remains dispatch-only after the upgrade. Complete these transition checks before activating the workflows or dispatching a release; copying only the new workflow over an old pending release state is not a safe migration.

### Apply and verify the update

1. Compare `copy/` with the repository and overwrite the repository files with the kit versions. Include the new `.github/workflows/beta.yml`, `scripts/New-BetaRelease.ps1` and `tests/Build/BetaRelease.Tests.ps1`. Replace `release-please-config.json` with the stable-only config; do not retain prerelease versioning settings. Normalize `source/` directories as described in step 5. Re-apply **Pipeline customizations** from `BUILDING.md` (step 5b); if a customization no longer fits, stop and ask.
2. Delete the obsolete paths explicitly listed under `Remove` in `kit-files.psd1`, including the old stable config, promotion/preparation/rollup scripts and their tests. These are known pipeline paths, not permission to delete other scripts. If a listed file contains unrelated custom behavior, stop and ask. Check that no active workflow/script/test references the removed implementation.
3. For each file in `adapt/`, port only pipeline-relevant changes and retain module-specific content. In particular replace the release-process section of `BUILDING.md` and update README references from **Prepare release** to stable PRs and **Publish beta**. Explain that stable is no longer an exact-source beta promotion and that repeated beta dispatches intentionally create new preview versions.
4. Outside an explicitly approved baseline repair from the transition checks, do not edit `.release-please-manifest.json`, `version.txt`, `CHANGELOG.md`, the source module version, or release labels. Do not rewrite or consolidate historical changelog entries.
5. Check the release gates: `release-please.yml` must not have a `push` trigger. Dispatch prepares PRs only; only a merged, same-repository pending release PR may finalize, and finalization must skip PR creation. Do not remove the two event-dependent `skip-github-*` flags. Check publishing wiring: both `build.ps1 -Task Test -TestSuite Module` and `-Task Package` in `release.yml` must receive `-Version $env:MODULE_VERSION`; otherwise beta tags would publish the stable baseline. Preserve publish-target/platform customizations and stable-only getps.dev updates.
6. Update the `Pipeline kit:` line in `BUILDING.md`. Run `./build.ps1 -Task Test -TestSuite Infrastructure` and the full verification from step 7. Build a local preview using `./build.ps1 -Task Build -Version <next-stable>-beta001`; inspect its numeric `ModuleVersion`, padded `Prerelease`, and short preview notes. Confirm tracked versions and changelog are unchanged. Do not dispatch a publishing workflow or create tags/releases as a test without approval.
7. Finish as in step 8, using `build: update build and release pipeline from PSLogs kit`. Report the stable baseline, old release-PR state, removed paths, local test/build results, preserved customizations, and any unverified live GitHub behavior. No pushes or remote mutations without approval.
